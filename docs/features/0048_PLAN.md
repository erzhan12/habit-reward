# Feature 0048: Streak-Only Reward Chance and Streak Freeze

## Description

Rewards are currently too easy to win. The no-reward probability is `max(base − habit.weight − streak × 2, 10)`, which gives a 52–90% win chance per completion. This feature replaces it with a chance that depends only on the habit's streak, and adds a per-habit streak freeze.

- **New chance:** `p(s) = 20 + 30 × (1 − e^(−(s−1)/5.5))` percent, capped at 50. `s` is the streak day of the completion being rolled (`HabitLog.streak_count`, where 1 is the first day or the first day after a break).
- **Expected wins:** about 13.2 per habit per 30 perfect days, against about 23.2 today.
- **Break:** a broken streak is a hard reset to `s = 1` (20%). There is no comeback bonus. `allowed_skip_days` and `exempt_weekdays` behave exactly as today.
- **Launch reset:** every streak restarts at `s = 1` on the day 0048 ships (Open Question 11). No logs are deleted; completions before the reset simply stop counting toward the current streak. Historical "longest streak" stats are kept.
- **Freeze:** if a completion wins no prize, roll a 10% chance of a freeze. A habit holds at most one unused freeze. A freeze covers one missed day and preserves streak and chance. It is spent automatically by a periodic bot job at the end of the first missed day beyond `allowed_skip_days`, whether or not the user comes back (Duolingo-style): if the user also misses the next day, the streak breaks and the freeze is already gone.
- **Removed inputs:** `Habit.weight` and `User.no_reward_probability` no longer affect the chance. The DB fields stay.
- **Unchanged:** a roll on every completion of every habit, `max_daily_claims`, `select_reward()` internals, no rarities, and the exact % on the dashboard.

## Algorithm

### 1. Chance

```
calculate_reward_chance(s):
    s = max(1, int(s))
    p = BASE + BONUS * (1 - exp(-(s - 1) / TAU))
    return min(p, CAP)          # percent, float
```

The roll is `select_reward(effective_no_reward_probability=100 − p, …)`. `HabitLog.total_weight_applied` keeps storing `100 − p`, so its meaning ("effective no-reward %") is unchanged. `habit_weight` is still written as a snapshot because the column is NOT NULL.

### 2. Gap rule: what "one missed day" means (decided; Open Question 2)

For a gap between a completion on local date `L` and either the next completion on `D` or, for the open trailing gap, the user's local today `T`:

- `missed` is the list of non-exempt local dates strictly between `L` and `D` (or `T`). This is the same counting as today. For the trailing gap only days that have already ended (`< T`) count.
- `A = habit.allowed_skip_days`.
- The **guard day** is `c = missed[A]`: the first missed day beyond the allowance, the day the streak would break. It exists iff `len(missed) ≥ A + 1`.
- The freeze **covers** `c` if a SPENT event exists for `(habit, c)`, or (catch-up, §3) a usable freeze is in inventory.

| Condition | Outcome | Freeze |
|---|---|---|
| `len(missed) ≤ A` | CONTINUE, `s = prev + 1`. Identical to today | untouched |
| `len(missed) == A + 1` and the freeze covers `c` | FREEZE_SAVED, `s = prev + 1` | spent for `c` |
| `len(missed) ≥ A + 2` and the freeze covers `c` | FREEZE_BURNED, `s = 1` (20%) | spent for `c`; the streak still breaks on the next missed day |
| `len(missed) ≥ A + 1`, no freeze | RESET, `s = 1` (20%) | none |

- **Priority:** `allowed_skip_days` and `exempt_weekdays` absorb misses first, for free and per gap as today. The freeze only ever covers the single day `c`.
- **Miss of 2+ days beyond the allowance (Duolingo-style):** the freeze is spent at the end of `c` regardless of what happens next. If the user also misses the following day, the streak resets and the freeze is gone.
- **Usable** means `habit.freeze_count > 0` and the freeze actually held was not won on or after the day it covers. Let `H` be the habit's EARNED event with `state='held'`:
  - `H` is None (untracked admin grant) or `H.earned_on` is null (non-completion grant): usable.
  - otherwise usable iff `H.earned_on < covered_date`.

  The rule reads `earned_on` from the held event, never joins through `habit_log` and never uses "latest EARNED", so it is correct after undos and returns. It only matters for backdates: a freeze won on `L` or earlier always has `earned_on < c`.
- **Spend:** consume the held freeze: `try_consume_freeze`, set `H.state='spent'` (if `H` exists), create SPENT with `earned_event=H` (null for an untracked freeze).
- **Streak days:** frozen and skipped days do not add to `s`; the next completion is `prev + 1`.

### 3. When the freeze is spent

**Primary: the periodic job.** `freeze_service.burn_due_freezes()` runs every `FREEZE_JOB_INTERVAL_SECONDS` (900 s) from the bot JobQueue, so a freeze is spent within ~15 minutes after the user's local midnight. For every active habit with `freeze_count > 0` and at least one log:

The candidate list (habits with `freeze_count > 0`) is read outside any transaction; everything else for one habit runs in `FreezeService._burn_one_sync(habit_id)` inside a single `transaction.atomic()` (§4 "Transaction execution"):

1. Lock and re-read the habit row with `select_for_update()` (the same lock every freeze-touching transaction takes first, §4), and re-check `freeze_count > 0`.
2. **Inside the same transaction**, `T = get_user_today(user.timezone)`, `L` = the latest log date, build the trailing `missed` (ended days only). Computing the gap inside the transaction means a backdate that filled `c` and committed first is seen here, and a backdate that commits later sees this SPENT event and returns the freeze in its recalculation (§5). The job never spends for a day that already has a log.
3. If `len(missed) ≥ A + 1`, `c = missed[A]`, and the freeze is usable for `c`: in an inner savepoint, `try_consume_freeze` and create SPENT `(habit, covered_date=c, habit_log=None)`.
   - A lost compare-and-set, or an `IntegrityError` on `uniq_freeze_spent_habit_day`, means another process or the catch-up already did it: roll back the savepoint and skip.
   - Lock contention goes through the shared bounded retry (§4); if retries are exhausted the habit is skipped for this tick and logged at WARNING, so one busy habit does not stop the sweep.
   - Test: a backdate onto `c` committed between the candidate read and `_burn_one_sync` → no spend; a backdate onto `c` committed after the spend → freeze returned by recalculation.
4. Invalidate the user's streak cache via `transaction.on_commit` (§4). Log the number of freezes spent.
5. **Notify (decided; Open Question 3).** After the transaction commits, only the run that actually created the SPENT event sends one Telegram message `FREEZE_SPENT_NOTICE` to `user.telegram_id` in `user.language`. This makes it exactly-once per spend without extra state: a run that lost the race sends nothing.
   - Several habits spent in the same run for one user are grouped into one message.
   - Send failures (`Forbidden` when the bot is blocked, network errors) are logged and not retried; the spend stays.
   - A catch-up spend in a completion sends nothing extra: the completion message already says `FREEZE_USED` / `FREEZE_BURNED`.
   - If the job was down and the trailing gap already has `≥ A + 2` ended missed days (the streak is broken despite the freeze), send nothing: "complete today to keep your streak" would be false. Use the gap length, not `c < T − 1`, so exempt weekdays between `c` and today do not suppress a valid notice.
   - No "at risk" evening warning; that belongs with the 0047 reminders.

The job does not iterate users by "is it midnight now"; the condition is purely date-based and idempotent, so any run after midnight does the right thing and duplicate runs (several processes, overlapping ticks) are harmless.

**Catch-up: the job is not guaranteed to have run.** JobQueue starts only on the first webhook update after a restart (`webhook_handler.py:135`), and the process may be down at midnight. So:

- `process_habit_completion` (§4 step 2) and backdate recalculation (§5) perform the same spend for `c` if no SPENT event exists yet and a usable freeze is in inventory. The result is identical to what the job would have done.
- Read paths never write. They predict with the same rule: a habit whose trailing gap has `c` and a usable unspent freeze is displayed as if the freeze were already spent (no ❄️ chip, "freeze used for c").

**Spends are not tied to completions.** A freeze is spent because day `c` ended unfilled, not because the user came back. Undoing a later completion therefore does not return the spend for the guard day (§6); only filling `c` or shrinking the gap by a backdate does (§5). The one exception is a surplus spend after an undo merges two gaps, which §6 step 3 returns.

### 4. `process_habit_completion` (new order)

Validation and the duplicate pre-check stay as they are.

**Transaction execution (required).** The existing `_atomic()` (`habit_service.py:74`) enters `transaction.atomic()` and then yields to the event loop at every `await` on an async repository (`repositories.py` wraps each ORM call in its own `sync_to_async`). Two overlapping coroutines on the same thread-sensitive connection then nest as savepoints of each other: one call's rollback can discard the other's committed-looking work, and constraints cannot repair that. So steps 1–8 below, the undo (§6), the backdate recalculation (§5), and each habit in the freeze job (§3) run as **one synchronous function wrapped in a single `sync_to_async(..., thread_sensitive=True)` call**, with `transaction.atomic()` inside it and no `await` between BEGIN and COMMIT:

- `HabitService._commit_completion_sync(...)`, `_revert_log_sync(...)`, `FreezeService._burn_one_sync(habit_id)`.
- They call new sync repository methods (`*_sync`, like the existing admin pattern) so DB access still goes through `src/core/repositories.py`; `select_reward`'s DB reads move into a sync helper (`RewardService._select_reward_sync`) used only here. The async public API of the services is unchanged.
- The random draws (`random.choices`, `freeze_service.roll()`) happen inside the sync function too, so tests patch the same module-level `random`.
- **Settle due spends first (all mutating paths).** Right after taking the habit lock, completion (today and backdate), undo, and admin revert run the trailing-gap catch-up exactly as the job would (§3), *before* inserting or deleting any log and before any return/reconciliation. The final state then never depends on whether the job ran before the user acted. Example: earn F1 Mon, spend Tue, win F2 Wed, miss Thu, backdate Tue on Fri → with or without the Thursday-night job run, F2 is spent for Thu first, then the Tue backdate returns F1 into an empty inventory (F1 `held`). Test each mutating path under both job schedules and assert identical final state.
- **Settings edits reconcile too.** Changing `allowed_skip_days` or `exempt_weekdays` (API `habits.py:366`, web, bot, admin) changes every gap's `missed` and guard day. The update runs as one more transaction function under the habit lock, in this order: (1) settle due spends **under the old settings** (exactly what the job would have done by now), (2) write the new settings, (3) run §5 reconciliation over all gaps from `streak_epoch` (or the first log) onward, including the trailing gap. Settling after the write would let job timing decide which freeze survives: `A=0`, earn F1 Mon, spend Tue, earn F2 Wed, miss Thu, raise `A` to 1 on Fri → if the Thursday job ran, F2 is spent for Thu and both returns keep F1 held (F2 forfeited); if not, no Thu spend exists under `A=1` and the Tue return forfeits F1 against held F2. A later undo of Monday then diverges. Test this sequence under both job schedules and assert identical final state. A spend whose gap no longer needs it (now `≤ A`) is returned; a spend whose guard day moved is relocated if eligible. Test: freeze spent for Tue, raise `allowed_skip_days` to 1 → the spend is returned and Thursday's completion continues the streak; same result under both job schedules. Test (exempt edit): `A=0`, complete Mon and earn a freeze, miss Tue+Wed, job spends it for Tue, on Thu add Tuesday to `exempt_weekdays` and complete → the SPENT event is moved to Wed (new `c`), Thursday's log continues the streak (`prev + 1`), not RESET.
- **Cache invalidation after commit.** Streak-cache invalidation (`streaks:v2:{user_id}`) is registered with `transaction.on_commit(...)` inside each transaction function, never called before COMMIT; otherwise a concurrent reader can repopulate the cache from the pre-commit state for 5 minutes (`streak_service.py:326`). Test: a reader running between the write and the commit does not leave a stale cache entry.
- **Shared per-habit serialization.** Every one of these transaction functions (completion, backdate recalculation, undo, the job's `_burn_one_sync`, admin revert) starts by locking the habit row: `Habit.objects.select_for_update().get(pk=habit_id)`, before reading logs or events. On PostgreSQL this makes all freeze-touching transactions for one habit run one after another, so a backdate cannot reconcile against a state the job is about to change. On SQLite `select_for_update` is a no-op, but SQLite transactions are serializable (one writer at a time; a reader that tries to write after another writer committed fails instead of writing stale data), so the same anomaly turns into a lock error handled by the retry below.
- **Bounded retry on lock contention.** The async wrapper of each transaction function catches `OperationalError` whose message contains `database is locked` (SQLite) or a serialization/deadlock error (PostgreSQL), and re-runs the **whole** sync function up to 3 times with 50/150/400 ms backoff. A retry is safe because nothing was committed; the random draws are made again inside the new attempt. After the last attempt it raises `ServiceBusyError`; the API maps it to 503 (`habits.py:472` today maps only `ValueError("already completed")` → 409), the web flash and the bot show "Busy, please try again". The job uses the same wrapper and, if retries are exhausted, skips the habit until the next tick. The `transaction_mode=IMMEDIATE` SQLite setting would remove most of these errors but is a global change, kept as a separate follow-up.
- Race tests use **separate DB connections** (threads with their own connection, `TransactionTestCase`), not overlapping coroutines on one connection: (a) job vs backdate onto `c` in both commit orders → never a SPENT on a day with a log; (b) two completions of the same habit/day → one log; (c) lock contention → retry then success, and exhausted retries → `ServiceBusyError`/503.
- Test: two overlapping `process_habit_completion` calls on the same connection (one valid, one duplicate that hits `uniq_habitlog_habit_day`) leave exactly the valid log, its progress increment, and its freeze effects.

Inside that one synchronous `transaction.atomic()` block:

1. `res = streak_service.resolve_streak_for_completion(user.id, habit, target_date)`. For today and for backdates it uses `get_last_log_before_date`.
2. Catch-up (§3): if `res.needs_catchup_spend` (guard day `c` exists, no SPENT event for it, usable freeze in inventory), call `habit_repo.try_consume_freeze(habit.id)` and create SPENT `(c, habit_log=None)`.
   - The consume + SPENT insert runs in an **inner `transaction.atomic()` (savepoint)**. An `IntegrityError` is caught *outside* that inner block, so the savepoint is rolled back and the outer transaction stays usable; catching it inside the outer atomic and then querying raises `TransactionManagementError`. Same pattern in the job and in recalculation. Test with a real constraint violation, not a mock.
   - If the compare-and-set fails or the SPENT insert hits `uniq_freeze_spent_habit_day`, someone else got there first: re-read the SPENT event for `c`. If it exists, keep the FREEZE_SAVED / FREEZE_BURNED outcome.
   - Otherwise, before falling back, re-check for an existing log on `(habit, target_date)`. If one exists, raise "already completed": the race was a duplicate submit of this same completion, whose spend is not yet visible. Only if no log exists, fall back to RESET (`s = 1`).
   - **Dependency on 0033.** The duplicate re-check is still check-then-act. Two concurrent submits can both pass it, and without `uniq_habitlog_habit_day` the loser would commit a second log with `s = 1` next to the winner's `s = prev + 1`. With 0033 applied, the loser's insert in step 4 fails and the whole block rolls back. So without 0033 this edge case is *not* handled, only made rare. That is why Open Question 7 must be settled before PR B and 0033 is treated as required, not optional.
   - `res.outcome` is FREEZE_SAVED (`s = prev + 1`) or FREEZE_BURNED (`s = 1`) whether the spend happened now or earlier in the job.
3. `p = calculate_reward_chance(s)`, then `select_reward(100 − p, user_id, target_date=today)` (unchanged call), then `update_reward_progress` on a win.
4. Create the `HabitLog`. An `IntegrityError` from `uniq_habitlog_habit_day` propagates out of the outer `transaction.atomic()`, rolling the whole block back; the async wrapper catches it there and raises `ValueError("… already completed on …")`.
5. (No SPENT event is created here; step 2 already did it if needed.)
6. If `target_date < today`, run `recalculate_streaks_after_backdate`. It moves inside the transaction and may return a freeze.
7. Freeze roll, last, against the final inventory: if `not got_reward`, re-read `freeze_count`. If it is 0 and `freeze_service.roll()` succeeds, call `try_grant_freeze` and create the EARNED event with `habit_log`, `earned_on = target_date`, and `state='held'`.
   - "No prize" means `select_reward` returned `None` for any reason, including an empty or capped pool.
   - A habit that just spent its freeze is eligible in the same completion.
8. Register streak-cache invalidation with `transaction.on_commit` (§4).

After commit: audit snapshot (add `reward_chance`, `freeze_used`, `freeze_burned`, `freeze_covered_date`, `freeze_won`), WebSocket notify, and the populated `HabitCompletionResult`. `freeze_used` means the outcome was FREEZE_SAVED and `freeze_burned` means FREEZE_BURNED, regardless of whether the job or the catch-up did the spend.

The freeze chance per completion is `(1 − p) × 10%`: 8% at `s = 1`, about 5% at `s ≥ 30`.

### 5. Recalculation after a backdate

A backdate only fills a day, so it can only split or shrink gaps. Recalculation walks every gap from the backdated log onward, **including the trailing gap up to today**, and matches existing SPENT events to gaps by **calendar interval, before exempt-day filtering**: an event belongs to the gap `(prev_log_date, closing_log_date)` (exclusive both ends; for the trailing gap `(last_log_date, today]`) that contains its `covered_date`. Matching through `missed` would orphan an event whose `covered_date` became exempt after a settings edit (§4); with interval matching such an event is still in its gap and gets moved to the new `c` (or returned) by the rules below. Intervals are disjoint, so each event belongs to exactly one gap.

| Gap after the backdate | Streak of the log closing it | SPENT event in this gap |
|---|---|---|
| `len(missed) ≤ A` | `prev + 1` | Delete it and `try_grant_freeze` (freeze returned). The return is dropped silently if the habit already holds one |
| `len(missed) ≥ A + 1` and an event exists | `prev + 1` if `len == A + 1`, else `1` | Keep one; see "several events in one gap" below |
| `len(missed) ≥ A + 1`, no event | `1` | none |

- **Several events in one gap.** A gap can hold more than one SPENT event after an undo merges two gaps (§6). A gap needs at most one spend, for its guard day `c`. Reconcile per gap, deterministically:
  An event is **eligible for `c`** if its freeze could have covered `c`: `earned_event` is null (untracked) or has null `earned_on`, or `earned_event.earned_on < c` (the usable rule of §2 applied to that spend's own freeze).
  1. If an event already has `covered_date == c` and is eligible, keep it.
  2. Otherwise keep the eligible event with the earliest `covered_date` and move it to `c`. Its old date is not `c`, and `c` has no other event in this habit (events in other gaps cover days of those gaps), so the update cannot hit `uniq_freeze_spent_habit_day`.
  3. If no event is eligible, keep none: the gap gets no spend (RESET for its closing log).
  4. Every other event in the gap is surplus: return it with the returning rule below (held or forfeited), then delete it. Process surplus deletes **before** the move in step 2, so no intermediate state violates uniqueness.
  - Test (provenance): complete Mon, miss Tue, win F on Wed, spend F for Thu, complete Fri, undo Wed → merged gap Mon→Fri has `c = Tue` and F has `earned_on = Wed`, so F is not eligible: it is returned, the gap resets, and a later backdate of Wed does not get credit from F.
  - Test: earn Mon, spend Tue, complete and re-win Wed, spend Thu, complete Fri, undo Wed, then backdate the Sunday before → exactly one SPENT on Tue, the Thu spend returned, no `IntegrityError`.
- A SPENT event whose `covered_date` now has a log (the user backdated the covered day) is deleted and the freeze returned.
- **Returning a freeze** (any row above that deletes a SPENT event `S`): `try_grant_freeze`. If it succeeds, set `S.earned_event.state='held'` (if `S.earned_event` exists; an untracked spend returns as an untracked freeze). If it fails because the habit already holds a freeze, set `S.earned_event.state='forfeited'`. Then delete `S`. This keeps the provenance invariant: exactly the freeze in inventory is `held`.
- Recalculation never creates a new spend for a closed gap; the only spends a backdate can create are the catch-up for the gap the backdated completion itself closes (§4 step 2) and for the trailing gap, both exactly as the job would have done them. Past rolls are not re-rolled, as today. The procedure is idempotent.

### 6. Undo (`_revert_log_transaction`, before deleting the log)

0. Lock the habit row and **settle due spends first** (§4): run the same catch-up the job would do for the current trailing gap (and nothing else). This makes the undo result independent of whether the job has already run. Example: earn Mon, miss Tue, undo Mon on Wed — with or without a prior job run, Tue's spend exists before step 1, so the Monday freeze is `spent`, not `held`, and step 1 keeps its provenance. Test both job schedules give identical final state.
1. If the log has an EARNED event `E` with `E.state == 'held'`: `try_consume_freeze`, delete `E`, and set `freeze_revoked`. The held freeze is exactly the one this completion won, so revoking it is always correct.
   - `E.state == 'spent'` or `'forfeited'`: the freeze it won is not in inventory any more. Keep `E`; the log delete sets its `habit_log` to NULL and `earned_on` stays. A freeze currently held that came from a different win (for example one returned by a backdate) is never touched.
   - Test the sequence: earn F1, spend F1, earn F2, spend F2, backdate returns F1 (F1 `held`), undo F2's earning log → F1 stays held, `freeze_count = 1`, no revoke.
2. Delete the log. No events cascade; any event still pointing at it is a kept EARNED event and gets `habit_log = NULL`.
3. Reconcile the gap the deleted log used to split: its predecessor's gap and its successor's gap (or the trailing gap) are now one. Apply the §5 per-gap reconciliation to that merged gap and recompute streaks from the successor onward exactly like §5 recalculation (same function, started at the successor). The covered days stayed missed, so the spend for the merged gap's guard day stays; only surplus spends of the merged gap are returned.

Undoing the latest completion reopens the trailing gap. If that gap already had a SPENT event it keeps it; if it now reaches `A + 1` ended days with no spend, the next job run (or catch-up) spends a freeze as usual.

The admin action applies the same steps through `revert_for_log_sync`. A revert path that skips step 1 would leave a won freeze in inventory after its completion was undone, so all three paths must call the shared helper.

### 7. Display

`get_streak_states` returns, per habit:

- `streak`: 0 if broken.
- `freeze_count`: the effective inventory, i.e. `habit.freeze_count` minus a spend the job has not done yet (§3 prediction).
- `freeze_used_for`: the guard day `c` if the trailing gap is alive only thanks to a spent (or predicted) freeze, else null.
- `freeze_at_risk`: today is not an exempt weekday for this habit, the habit is not completed today, the trailing gap has exactly `A` ended missed days, and a usable freeze is held (test: exempt today → false). Meaning: "skip today and the freeze is spent tonight".
- `next_streak`: `streak + 1` if alive, else 1.

The dashboard chance is `round(100 − today_log.total_weight_applied)` if the habit is completed today (the stored snapshot of the chance that actually applied; recomputing from the streak would be wrong after a backdate rewrote `streak_count` or for a pre-deploy log on the epoch day), else `round(calculate_reward_chance(next_streak))`. This removes the existing one-step mismatch between the displayed and the rolled chance. A habit with no logs shows 20%.

### 8. Launch reset (`Habit.streak_epoch`)

- **Predecessor rule:** when looking for the previous completion `L` (completion, backdate recalculation, read paths, the freeze job), logs with `last_completed_date < habit.streak_epoch` do not exist. A first completion on or after the epoch therefore gets `s = 1`.
- **Effective streak on the epoch day:** a log dated exactly `streak_epoch` has no counted predecessor, so its effective streak is 1 regardless of the stored `streak_count` (which may be a pre-reset value from a completion before the deploy). Whenever the engine uses a predecessor's streak (`prev + 1`, recalculation, `get_streak_states`), it uses `effective_streak(log) = 1 if log.last_completed_date == habit.streak_epoch else log.streak_count`. Tomorrow's completion is therefore 2. No rows are rewritten.
- **Backdates before the epoch** (possible during the first 7 days) are allowed. They have no predecessor, get `s = 1`, roll at 20%, and never affect streaks on or after the epoch. Recalculation never walks below the epoch.
- **Freeze job:** a habit whose only logs are before the epoch has no trailing gap and is skipped.
- **Stats:** "longest streak" queries (`repositories.py` ~883, ~1016, ~1074) read stored `streak_count` and keep showing historical records; they are not filtered by the epoch.
- The field is generic, so a later "reset this habit's streak" admin action can reuse it; out of scope here.

## Edge Cases

- **Miss of 2+ days.** With `A = 0` and a freeze, last completion Monday:
  - Shortly after Tuesday midnight the job spends the freeze for Tuesday. Return on Wednesday: streak continues.
  - Return on Thursday: Wednesday is uncovered, so reset to 20%. The freeze was already spent for Tuesday and is gone.
  - Bot down Monday night to Thursday: the Thursday completion catches up, spends the freeze for Tuesday (FREEZE_BURNED), and resets. Same result as if the job had run.
- **Job timing.** Up to `FREEZE_JOB_INTERVAL_SECONDS` after local midnight the freeze is still in the DB inventory; read paths already show it as spent (§3), so the user sees no difference.
- **Several processes.** If the web workers and the polling bot (`src/bot/main.py`) both run the JobQueue, they may run the job concurrently. The compare-and-set plus `uniq_freeze_spent_habit_day` make the second run a no-op.
- **Freeze with `allowed_skip_days`.** With `A = 1`, missing Tuesday uses the grace day and no freeze. Missing Tuesday and Wednesday uses grace for Tuesday and the freeze for Wednesday (spent after Wednesday midnight). Missing three days: the freeze is spent for Wednesday and the streak still resets on Thursday. Exempt weekdays never count toward `missed`.
- **Timezone.**
  - Every date (`target_date`, `last_completed_date`, `covered_date`) is the user's local calendar date from `get_user_today(user.timezone)`. There is no UTC date arithmetic and no DST sensitivity.
  - Two UTC-default callers are fixed: `habit_custom_text` and the API `streaks.py`.
  - A user changing timezone can shift "today" by one day, which can create or remove one missed day. This is an existing property, documented and not handled.
- **Backdated completions (7-day window, unchanged).**
  - The backdated completion resolves its own gap. Normally the job has already spent a freeze there; if not, the catch-up may spend one, but only one won before the covered day.
  - It rolls a prize at `p(s at that date)` and a freeze by the normal rule.
  - Filling the day a freeze covered, or shrinking the gap to within `A`, returns the freeze through recalculation. This is the only way a spent freeze comes back.
  - `select_reward` still checks `max_daily_claims` against today for a backdated completion. This is an existing quirk, left unchanged.
- **Undoing a completion.**
  - Undoing the completion that followed a frozen day does not return the freeze: the day stayed missed.
  - Undoing the completion that won a freeze revokes it.
  - If that freeze was already spent, it stays, and so does its EARNED event, with `habit_log = NULL` and the original `earned_on`. This is reachable only through a by-log-id or admin revert of a non-latest log.
  - Redoing after an undo rolls afresh, as rewards do today.
- **Admin-granted freeze.** The admin "Grant freeze" action creates no EARNED event. It is an untracked freeze (no `held` EARNED), usable for any covered day, and spent by the job normally with `earned_event = NULL`. "Remove freeze" marks a `held` EARNED as `forfeited` if one exists; both run under the habit lock, and the form never writes `freeze_count` directly.
- **Two completions on the same day.** The same habit is rejected by the pre-check and by 0033, so there is no second roll, spend, or win. Different habits are independent: each has its own streak, freeze, and roll. `max_daily_claims` still caps pieces per reward per day across habits; a capped-out pool yields "no prize" and a freeze roll.
- **Idempotency.**
  - One log per `(habit, date)`.
  - One EARNED event per log; SPENT events never reference a log.
  - One SPENT event per `(habit, covered_date)`.
  - Inventory changes are conditional `UPDATE`s, so a retried request, a double undo, a rerun of recalculation, or overlapping job runs cannot double-apply.
  - The session flash is popped once.
- **Races and concurrent completions.**
  - The authoritative guards are the DB constraints and the compare-and-set updates, not the Python pre-checks.
  - The loser of a double-submit fails on `uniq_habitlog_habit_day`; its progress increment and freeze changes roll back and it gets "already completed" (409 in the API).
  - A lost freeze compare-and-set (against another completion or the job) is handled in step 2 of §4.
  - `select_for_update` is not relied on; it is a no-op on SQLite.

## Risks

- **Abrupt behaviour change.** Chances drop from 52–90% to 20–50% at deploy, and every streak restarts at 1. Users with long streaks will notice; consider an announcement in the bot (not part of this plan).
- **Duolingo-style burn is harsher.** A freeze is lost even when it cannot save the streak (2+ missed days). The "at risk" and "used for" hints and README copy explain it.
- **Job reliability.** JobQueue starts only on the first webhook after a restart, and several processes may run it. Correctness does not depend on the job: catch-up in completions and backdates plus prediction on read paths give the same result, and the job is idempotent. Without the job, the only visible difference is the DB inventory lagging until the next completion.
- **Job cost.** Each tick scans habits with `freeze_count > 0`, at most one per habit, with one "latest log" query each. Fine at current scale; index on `freeze_count` is not needed yet.
- **Async transactions.** `_atomic()` with coroutines on a shared thread-sensitive connection can interleave as savepoints; constraints cannot repair that. 0048 avoids it for every path it touches by running each transaction as one sync function (§4 "Transaction execution"). Other existing `_atomic()` callers keep the hazard; out of scope.
- **Migration 0033** fails if prod has duplicate logs, and it is required for PR B (§4 step 2), so duplicates block the whole release until resolved. The theme-choices drift may leak into `makemigrations`.
- **Undo/redo re-rolls.** This is farmable today for prizes; the freeze adds a second farmable outcome.
- **Three revert paths** (service, API by log id, admin raw ORM) must all reverse freeze events. Undo now reconciles the merged gap and recomputes the successor's streak (§6 step 3); the successor's own successors are recomputed the same way as backdate recalculation, so the old "mid-history revert does not recalculate" gap is closed for 0048.
- **Cache.** The value shape changes, hence the key bump. Staleness of up to five minutes across midnight is pre-existing.
- **`max_daily_claims`** remains check-then-act under concurrency (existing).
- **Kazakh copy** needs a native review.
